## Context

Баланс живёт в литерале `defaultSpaceshipSimulationConfig`
(`packages/game-core/src/spaceshipSimulation.ts`), а модель врага бинарна: параметры лежат плоскими
полями `gunshipHp`/`carrierHp`/`gunshipRadius`/…, и выбор между ними сделан тернарниками
`isGunship ? A : B` в шести местах `combat.ts` — выбор снаряда, пересчёт cooldown, `moveEnemy`,
`spawnEntity`, `createWavePlan`, начисление credits. Дисплей устроен так же:
`if (kind === "gunship") … else …`, поэтому третий kind молча отрисовался бы силуэтом carrier.

Ограничения, которые нельзя нарушить:

- `packages/game-core` остаётся чистым: без Phaser, React, DOM, сети, wall-clock и `Math.random`.
  Вся случайность — из seeded domains, весь шаг — чистая функция.
- Run воспроизводим из `(runSeed, waveNumber)`; порядок обращений к RNG — часть контракта, его
  изменение ломает существующие тесты детерминизма.
- Entity caps `40/16/96/12/32` и общий 196 продублированы константой `COMBAT_ENTITY_CAPS` в
  `packages/protocol` и используются как `.max()` в схемах снапшота.
- Сервер до сих пор не читал и не писал файлы; персистентности нет вообще.
- Авторизация служебных endpoints уже решена для `/stats/rooms`: без пароля — только loopback, с
  паролем — Basic `admin:<password>`, сравнение через `timingSafeEqual`.

## Goals / Non-Goals

**Goals:**

- Данные вместо ветвлений: поведение и стоимость enemy kind описаны одной записью таблицы, новый тип
  добавляется записью, а не правкой шести мест.
- Точный контроль над началом кампании при сохранении бесконечного run.
- Редактирование баланса без коммита и передеплоя, с валидацией одними и теми же схемами на сервере
  и в UI.
- Детерминизм и воспроизводимость run сохраняются в полном объёме.

**Non-Goals:**

- Contact damage для enemy ships, архетипы `charger` и `support`, межвражеские эффекты.
- Многофазные боссы с собственным lifecycle, телеграфами и лутом.
- Горячее применение баланса к идущему бою.
- Редактирование entity caps, база данных, аутентификация сложнее Basic-auth, раздача собранной
  админки самим сервером.

## Decisions

### Таблица архетипов вместо плоских полей конфигурации

`CombatConfig` теряет `gunship*`, `carrier*`, `hostileBullet*`, `missile*` и получает
`enemyArchetypes: Readonly<Record<EnemyKind, EnemyArchetype>>`, где архетип описывает HP, радиус,
скорость, предпочитаемую дистанцию, оружие (`EnemyWeaponTuning`), `spawnCost`, `unlockWave`,
`scoreReward`, `creditReward`. Поля `asteroid*` остаются отдельно: астероид не `EnemyKind`, у него
свой lifetime и `origin`, а участие в бюджете волны описывается записью таблицы волн.

Альтернатива — оставить плоские поля и добавить `sniperHp`, `interceptorHp`, `bossHp` и так далее.
Отвергнута: число полей растёт как типы × параметры, а UI админки пришлось бы генерировать по
префиксам имён полей, что делает форму хрупкой к переименованию.

Ключевое следствие: рефактор идёт первым слайсом и не меняет ни одного числа, поэтому существующие
тесты game-core — включая тесты детерминизма — служат проверкой, что перенос данных ничего не
сдвинул.

### Снаряды несут damage и shield hit cost на инстансе

`HostileProjectileState` и `HomingMissileState` получают `damage`, `shieldHitCost`, а ракета ещё и
`turnRatePerSecond`, унаследованные от архетипа стрелка при создании. Так уже устроен астероид,
который несёт собственный `damage`.

Альтернатива — оставить значения в конфигурации и разрешать их по `kind` снаряда при попадании.
Отвергнута: снаряд переживает своего стрелка, и в момент попадания архетип источника уже недоступен,
поэтому разные типы врагов не смогли бы иметь разное оружие — а это ровно то, ради чего вводятся
sniper и interceptor.

### Гибридная кампания: явная таблица поверх процедурного директора

`WaveCampaign` = `waves: WaveDefinition[]` (явные волны 1..N, по умолчанию пусто) +
`director: DirectorTuning` (нынешние budget/HP/tempo ручки плюс `bossWaveInterval`).
`createWavePlan` при `waveNumber <= waves.length` строит план прямо из записей, без обращения к
spawn RNG за составом и без шафла; иначе работает нынешний бюджетный алгоритм, где `spawnCost` и
`unlockWave` берутся из архетипов.

Дефолт `waves: []` означает ровно нынешнее поведение, поэтому слайс кампании тоже проверяется
существующими тестами.

Альтернатива — полностью явная таблица без директора. Отвергнута: ломает требование бесконечного run
из `wave-campaign` и потребовала бы ввести victory-условие, которого в этом slice нет.

Порядок обращений к RNG для явных волн отличается от процедурных по необходимости: состав задан, RNG
за него не спрашивают. Точки появления при этом остаются seeded, так что воспроизводимость run по
`(runSeed, waveNumber)` сохраняется в обоих режимах.

### Сектор появления ограничивает seeded угол, а не заменяет его

Запись волны может задать сектор окружности; спавн выбирает угол внутри сектора тем же seeded
потоком. Фиксировать угол числом было бы проще, но это убрало бы вариативность внутри волны и
сделало бы повторные прогоны одинаковой волны визуально идентичными.

### Пресеты — JSON-файл, применение к новому run

Store читает файл при старте, держит разобранный пресет в памяти и отдаёт
`Partial<SpaceshipSimulationConfig>` в `tryStartRun`, где уже вызывается
`createSpaceshipSimulationConfig()` — фабрика валидирует результат. Merge в фабрике поверхностный,
поэтому store обязан отдавать `enemyArchetypes` целиком; частичный архетип отклоняется схемой, а не
доезжает до симуляции полупустым.

Применение только к новому run выбрано ради детерминизма: конфигурация зафиксирована на весь run,
поэтому `(runSeed, waveNumber)` по-прежнему полностью описывает происходящее, а дисплею не нужно
ресинкать геометрию посреди волны.

Альтернативы — env-переменные (не выражают таблицу волн), база данных (лишняя зависимость ради
одного документа), Colyseus room options (клиент не должен диктовать баланс: комнату создаёт
display, а он такой же недоверенный клиент, как контроллеры).

Запись атомарна: временный файл рядом с целевым и `rename`, чтобы прерванная запись не оставила
повреждённый пресет. Повреждённый или отсутствующий файл никогда не роняет сервер — работаем на
defaults и пишем одно предупреждение.

### Схемы баланса живут в protocol

`packages/protocol/src/balance.ts` реэкспортируется из `index.ts`. Один набор zod-схем валидирует
пресет и на сервере, и в формах админки, поэтому UI не может считать валидным то, что сервер
отклонит. `exports` пакета менять не нужно — он уже отдаёт `./src/index.ts`.

Схемы баланса не входят в версионируемый игровой контракт: `PROTOCOL_VERSION` бампается из-за
расширения `ENEMY_KINDS`, а не из-за них.

### Отдельное приложение `apps/admin` и dev-proxy вместо CORS

Консоль — четвёртое Vite-приложение на порту 5175 со структурой, скопированной с `apps/controller`,
и plain CSS: ни Tailwind, ни CSS-модулей в репозитории нет. `server.proxy` в `vite.config.ts`
направляет `/admin` на `http://localhost:2567`, поэтому запросы идут на собственный origin,
CORS-заголовки не нужны, а на dev-машине запрос приходит с loopback и пароль не требуется.

Альтернатива — страница на сервере по образцу `/stats/rooms`. Отвергнута: редактор таблицы волн на
inline-скрипте под жёстким CSP `script-src 'unsafe-inline'` быстро станет неподъёмным.

Для удалённого доступа нужен reverse proxy с TLS и `ADMIN_BALANCE_PASSWORD` — то же ограничение уже
действует для статистики комнат.

### Полная таблица визуалов на дисплее

`ENEMY_VISUALS: Record<EnemyKind, { color, draw }>` вместо `if/else`: пропущенный kind становится
ошибкой компиляции, а не тихой подменой силуэта. Геометрия масштабируется от `entity.radius`,
который сейчас у врага игнорируется — без этого boss с радиусом 90 нарисовался бы размером с
gunship. HP-бар только у boss: 900 HP без индикатора читаются как неубиваемая цель.

## Risks / Trade-offs

- **Рефактор архетипов сдвигает порядок обращений к RNG и ломает воспроизводимость run** → слайс 1
  выполняется без изменения чисел и без изменения последовательности вызовов; тесты детерминизма
  game-core прогоняются до и после и должны остаться зелёными.
- **Оператор задаёт таблицу волн, которая делает игру непроходимой или тривиальной** → монотонность
  сложности гарантируется спекой только для процедурного хвоста; явная таблица авторитетна как
  задана, а консоль показывает суммарную стоимость волны рядом с бюджетом директора на том же
  номере, чтобы расхождение было видно.
- **Пять типов и залповый огонь босса увеличивают время шага симуляции** → `pnpm benchmark:combat`
  прогоняется после добавления типов; при просадке поднимаются `spawnCost` босса и sniper, а не
  caps.
- **Запись файла с нескольких процессов** → сервер однопроцессный (LocalDriver, без Redis), запись
  атомарна через rename; параллельная запись из двух вкладок админки приведёт к «побеждает
  последний», что для инструмента тюнинга приемлемо.
- **Admin API открыт на LAN при неаккуратном деплое** → по умолчанию доступ только с loopback,
  `X-Forwarded-For` не учитывается, удалённый доступ требует явного пароля.
- **Расширение `ENEMY_KINDS` ломает старых клиентов** → `PROTOCOL_VERSION` бампается до 15, старые
  create/join/gameplay сообщения получают `protocol_mismatch` до мутации состояния; server, display
  и controllers выкатываются вместе.

## Migration Plan

Развёртывание одномоментное: server, display и controllers обновляются вместе из-за бампа протокола.
Файл пресетов не обязателен — без него сервер работает на встроенных defaults, поэтому первый деплой
не требует подготовки данных. Откат — возврат предыдущей сборки; файл пресетов остаётся на диске и
игнорируется старой версией, поскольку она его не читает.

## Open Questions

- Нужны ли админке права на запуск и остановку run (сейчас run стартует только по готовности трёх
  контроллеров) — вне scope этого change, но всплывёт при тюнинге в одиночку.
- Понадобится ли отдельный «песочный» режим комнаты, где баланс применяется без живого экипажа —
  зависит от того, насколько неудобным окажется ручной прогон.
