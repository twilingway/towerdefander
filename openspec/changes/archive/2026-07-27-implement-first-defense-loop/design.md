## Context

Текущая комната синхронизирует lobby и тестовый счётчик, а `game-core` содержит только seeded random
и явные часы. Новый срез пересекает ядро, protocol, Colyseus state и оба клиента. Сервер остаётся
единственным источником истины; display и controller не рассчитывают результат боя.

Основные ограничения: детерминизм без wall clock внутри ядра, строгая runtime validation,
воспроизводимые тесты, небольшой публичный state и приемлемая работа в desktop Chromium/Firefox и
Android TV WebView.

## Goals / Non-Goals

**Goals:**

- получить короткий полностью завершаемый бой в двух секторах;
- отделить чистые переходы состояния от сетевого scheduler;
- атомарно обслуживать общую казну и повторную доставку команд;
- дать обоим клиентам достаточно данных для ручного игрового теста.

**Non-Goals:**

- финальная Phaser-графика, анимационная интерполяция и звук;
- пять волн, несколько типов врагов, способности, босс и поддержка 3–6 игроков;
- сохранение матча после уничтожения процесса сервера;
- скрытие небольшого публичного снимка по клиентским ролям.

## Decisions

### Чистое ядро с конфигурацией и immutable-переходами

`packages/game-core` владеет типами `DefenseConfig`, `DefenseState`, командами и функциями
`createDefenseState`, `advanceDefense` и `applyDefenseAction`. Функции возвращают новое состояние и
результат, не используют React, Phaser, Colyseus, timers или глобальную случайность.

Альтернатива — мутировать Colyseus Schema непосредственно в игровом цикле. Она проще в первом
коммите, но связывает правила с транспортом и делает повторяемость и property-like тесты заметно
сложнее.

### Fixed step на сервере, целочисленная математика в ядре

Комната запускает scheduler только в phase `active` и передаёт ядру ровно один настроенный шаг.
Прогресс, здоровье, золото и урон представлены целыми числами; конфигурация содержит все значения
прототипного баланса. Ядро не измеряет прошедшее реальное время и потому одинаково обрабатывает
одинаковую последовательность шагов.

Альтернатива — вычислять delta из `Date.now()`. Это ухудшает воспроизводимость, усложняет reconnect
и даёт разные результаты под нагрузкой.

### Два сектора и стабильное назначение по identity

Два игрока получают `sectorId` по порядку первого входа. Назначение хранится в авторитетном state и
сохраняется при reconnect. На этом этапе игрок изменяет только свой сектор; совместные действия на
соседнем секторе остаются для MVP.

Альтернатива — разрешить всем менять оба сектора. Это скрывает будущую роль персонального
контроллера и затрудняет проверку прав на команду.

### Команды проходят protocol → room → game-core

Protocol повышается до следующей версии и определяет строгие payload для `player:repair` и
`player:upgrade`: `protocolVersion`, `roomId`, `playerId`, `actionId`. Room сверяет room/player с
соединением, выводит sector из серверного назначения, проверяет phase и затем атомарно заменяет
state результатом ядра. После валидного envelope и совпавшей identity итог первой обработки
сохраняется в room-wide журнале `actionId`, включая `invalid_phase`, `insufficient_funds` и
`action_not_available`; повтор получает тот же итог без нового вычисления.

Альтернатива — не включать `playerId` и `roomId` в payload. Она компактнее, но нарушает проектный
инвариант расходующих ресурсы команд и усложняет диагностику повторной доставки между комнатами.

### Один компактный публичный игровой снимок

Colyseus state публикует целочисленные данные двух секторов, активных врагов, казны и результата.
Display и controllers получают один снимок: для двух секторов и небольшого числа врагов это упрощает
первый вертикальный срез. Клиенты не получают seed, внутреннее расписание spawn или deduplication
set.

Альтернатива — отдельные filtered views уже сейчас. Она полезна при большом мире, но преждевременно
усложняет schema и reconnect для текущего ограниченного состояния.

### Lifecycle scheduler принадлежит комнате

Scheduler создаётся при старте матча и останавливается при результате или уничтожении комнаты.
Завершённый снимок больше не продвигается. Reconnect не создаёт второй scheduler и не перезапускает
бой. Бой продолжает шаги, пока display/controllers находятся в grace period. После истечения grace
контроллера его сектор освобождается; обычный вход во время active занимает свободный сектор как
замена и получает текущий снимок.

Альтернатива — timer в display-клиенте. Такой клиент мог бы ускорить или остановить доверенную
симуляцию и не подходит для игры через интернет.

## Risks / Trade-offs

- [Рост Colyseus patch при большом числе врагов] → ограничить расписание первого боя и измерить
  размер/частоту patch до расширения волн.
- [Timer jitter на слабом Android TV или сервере] → ядро использует fixed steps, display только
  отображает состояние; catch-up policy добавить после профилирования.
- [Immutable core создаёт объекты каждый tick] → сохранить малое состояние сейчас и перейти к
  контролируемой мутации только по данным профайлера.
- [Один public snapshot раскрывает состояние соседнего сектора] → это допустимо для кооперативного
  прототипа; ввести role-filtered views до появления скрытой информации.
- [Повышение версии ломает старые открытые вкладки] → сервер отклоняет их `protocol_mismatch`, UI
  предлагает перезагрузить страницу.

## Migration Plan

1. Реализовать и покрыть тестами чистое ядро.
2. Повысить protocol и заменить signal-сообщение игровыми командами.
3. Расширить Colyseus schema и подключить scheduler с feature-complete room tests.
4. Обновить display/controller и browser E2E.
5. Развернуть clients и server одной версией; rollback выполняется возвратом всего релиза, без
   миграции постоянных данных.

## Open Questions

- Числа баланса первого боя остаются прототипными и будут уточняться после ручного прогона.
- Политика catch-up после длительной паузы event loop будет выбрана после измерений этапа MVP.
