## Context

- **Живая статистика.** `/stats/rooms.json` строится на каждый запрос: `matchMaker.query` по двум
  типам комнат, затем `createRoomStatsSnapshot` складывает метаданные
  (`apps/server/src/stats/snapshot.ts`). Люди считаются сокетами (`connections`), боты сокетов не
  держат.
- **Кто публикует.** Кампания пишет метаданные при создании, каждом входе, выходе, переподключении и
  закрытии (`queueMetadataUpdate`, запись сливается). Арена пишет их раз в секунду и при создании
  (`publishStats`). У арены нет `onDispose`.
- **Процесс один.** `defineServer` вызван без presence и driver, поэтому все комнаты живут в одном
  процессе, и `matchMaker.stats.local` видит их все.
- **Хранилище.** Базы нет. Сервер уже пишет JSON в том `space-api-data`, смонтированный в `/data`:
  `balance.json` (`BALANCE_PRESET_PATH`) и отчёты батчей (`STATS_BATCH_DIR`). Оба пишутся через
  временный файл и `rename`.
- **Доступ.** Страница и JSON закрыты `ROOM_STATS_PASSWORD` или loopback (`stats/access.ts`). В
  проде их проксирует только nginx админки.

## Goals / Non-Goals

**Goals:** рекорды и пики по дням, которые не теряют короткий пик, переживают перезапуск и не
касаются игры.

**Non-Goals:** история глубже суточных пиков, игровые рекорды, общий учёт нескольких процессов,
показ вне страницы статистики комнат.

## Decisions

### 1. Учёт в процессе, по метаданным комнат

`ServerRecords` в `apps/server/src/stats/records.ts` держит карту `statsId → connections` открытых
комнат. Комнаты отдают ему те же `RoomStatsMetadata`, что публикуют в матчмейкер:

- кампания — в `queueMetadataUpdate`;
- арена — в `publishStats`.

При уничтожении комната себя забывает: кампания в `onDispose`, у арены появляется свой `onDispose`.
После каждого `observe` и `forget` учёт пересчитывает людей (сумма `connections`) и комнаты (размер
карты), сверяет их с рекордами и с пиком текущих суток.

_Отвергнуто:_

- Опрос `matchMaker.query` по таймеру: асинхронный запрос раз в N секунд пропускает пик короче
  периода и работает впустую, пока сервер пуст.
- Подсчёт на запрос страницы: пик, пришедшийся на время, когда страницу никто не держал, теряется.

### 2. Файл JSON в томе, пишется только при росте

- **Путь.** `STATS_RECORDS_PATH`, по умолчанию `apps/server/data/stats-records.json` (каталог
  `data/` уже в `.gitignore`). Прод: `/data/stats-records.json`.
- **Документ:**
  `{ version: 1, allTime: { people: { value, atMs }, rooms: { value, atMs } }, days: [{ date: "YYYY-MM-DD", people, rooms }] }`.
  Сервер проверяет его вручную, как метаданные комнат в `snapshot.ts`: своей библиотеки схем у
  сервера нет, а заводить зависимость ради одного файла незачем. В `packages/protocol` документ не
  попадает, никакой клиент его не читает.
- **Когда пишется.** Только когда вырос рекорд за всё время или пик текущих суток. Одновременно идёт
  не больше одной записи. Изменения во время записи сливаются в одну следующую — с последним
  состоянием.
- **Как пишется.** Во временный файл в том же каталоге, затем `rename`, как у пресета баланса.
- **При запуске.** Файл читается один раз, в `index.ts` рядом с пресетом. Нечитаемый файл или файл
  чужой версии копируется в `.unusable`, и учёт стартует пустым.

_Отвергнуто:_

- **SQLite** — нативная зависимость в образе ради нескольких сотен строк.
- **Redis** — объявлен в зависимостях, но не поднят и не используется.
- **Запись на каждое изменение числа людей** — сотни записей в час без новой информации.

### 3. Сутки по часовому поясу сервера

Дата строки — календарный день момента наблюдения в часовом поясе процесса (`Intl.DateTimeFormat`).
Контейнер API в проде запущен с `TZ: Europe/Moscow` (`docker-compose.prod.yml`), так что сутки
московские. Страница подписывает таблицу поясом, который сообщает учёт, а тесты задают пояс явно.

_Отвергнуто:_ сутки по UTC — день оператора начинался бы в три часа ночи, а пояс в проде уже
настроен.

### 4. Что видит страница

`RoomStatsSnapshot` получает поле `records`: рекорды за всё время и пики за последние 30 дней, новые
сверху. Весь хвост истории в ответ не кладётся: страница опрашивает JSON каждые пять секунд, а
историю читает оператор, открыв файл.

Разметка:

- в `ROOM_STATS_HTML` появляется блок «Рекорды»: две карточки с числом и датой;
- под ним таблица «Пики по дням» с поясом в заголовке и колонками Дата, Людей, Комнат.

Правила доступа прежние, потому что поле едет в том же ответе.

### 5. Время снаружи

`ServerRecords` получает `now` и `write` через параметры, как `createRoomStatsSnapshot` получает
`nowMs`. Тесты проверяют рекорд, пик, смену суток и слияние записей без таймеров и без диска, а файл
проверяется отдельно на временном каталоге.

## Risks / Trade-offs

- [Процесс падает между ростом рекорда и записью] → рекорд потерян. Запись начинается сразу, окно —
  миллисекунды.
- [Сервер когда-нибудь станет несколькими процессами] → каждый процесс поведёт свой учёт, а файл
  будет перетираться. Сейчас процесс один; при переходе учёт переезжает в общее хранилище.
- [Метаданные арены приходят раз в секунду] → вход в матч учитывается с задержкой до секунды. Пик
  людей в матче держится минутами, и потерять его нельзя: число людей в матче меняется только входом
  и выходом.
- [Кампания закрывается через `disposeOnce`, но `onDispose` вызывается всегда] → учёт забывает
  комнату в `onDispose`, и двойное забывание безвредно.
- [Часы контейнера сбиты] → строка ляжет не в те сутки. Контейнер берёт часы хоста, отдельная защита
  не нужна.

## Migration Plan

1. Выкатка добавляет `STATS_RECORDS_PATH: /data/stats-records.json` в `docker-compose.prod.yml`.
   Первый запуск создаёт файл при первом росте.
2. Откат: предыдущая сборка файл не читает и не трогает, а новая при возврате продолжит с него.
