# Стиль кода SpaceShip Defender

Правила раскладки и роста кода. `AGENTS.md` описывает рабочие соглашения, `CLAUDE.md` — команды и
архитектуру; этот файл отвечает на вопрос «куда положить новый код, чтобы через месяц не
перекладывать». Читать перед тем, как заводить новый файл или добавлять ветку в существующий.

Правила выведены из разбора августа 2026: три `App.tsx` выросли до 2657, 1209 и 517 строк, а
одинаковые хелперы разошлись копиями между `apps/display` и `apps/controller`.

## Где живёт файл

Клиентские приложения раскладываются по владению, а не по слоям. Ни FSD, ни atomic design: экранов
единицы, а сущности уже описаны один раз в `packages/protocol`.

```text
apps/<app>/src/
  App.tsx        композиция и выбор маршрута, ничего больше
  model/         данные и логика без разметки: сессия комнаты, адаптеры, хуки, чистые функции
  screens/       экран целиком, вместе со своими частями
  components/    то, что нужно двум и более экранам этого приложения
  game/          только apps/display: Phaser
```

Маршруты живут в `App.tsx` и больше нигде: это единственное место, которое знает, какой адрес какому
экрану соответствует. Сам экран о маршрутизации не знает — он принимает пропсы, как любой другой
компонент, и не зовёт хуков роутера. Это не вкусовщина: подписка компонента на состояние роутера
будит его на каждом переходе, а в бою дисплей специально доведён до того, чтобы корень не
перерисовывался вовсе (см. «Что рисует картинку, а что рисует цифры»).

Компонент поднимается по этой лестнице ровно тогда, когда у него появляется второй потребитель:

1. используется одним экраном — лежит внутри папки этого экрана;
2. появился второй экран в том же приложении — переезжает в `components/`;
3. появился потребитель в другом приложении — переезжает в `packages/client-shared`.

**Второй потребитель считается экранами, а не файлами.** Компонент, который импортируют пять файлов
одного экрана, остался у одного потребителя и живёт в папке этого экрана. Пересчитывать по числу
строк `import` — самый частый способ поднять на ступень выше то, чему там нечего делать.

Обратное движение тоже допустимо: когда потребитель остался один, компонент возвращается внутрь
экрана. Копировать вместо подъёма нельзя — именно так появились четыре реализации прогрессбара.

## Размер модуля

`App.tsx` — только композиция: провайдер, layout, таблица маршрутов. Никакой сетевой логики, никаких
больших JSX-веток. Ориентир — 80 строк.

Потолок production `.ts`/`.tsx` — 500 строк. Файл крупнее либо режется, либо получает в шапке
комментарий с причиной, почему делить хуже. Тесты под потолок не попадают.

Ветка `if`/`switch`, которая растёт вместе с каталогом данных, — сигнал резать по таблице, а не
удлинять файл.

## Данные в UI

Презентационный компонент принимает чистые пропсы и не знает ни про контекст, ни про сеть. Это не
вкусовщина: компонентные тесты рендерятся через `renderToStaticMarkup`, без jsdom и Testing Library,
и компонент с хуком контекста потребовал бы провайдера в каждом тесте.

Подключение к данным живёт в `model/hooks/useX.ts` и вызывается на уровне экрана:

```tsx
<TeamUpgradePanel {...useTeamUpgrade()} />
```

Стор не вводим. Trusted state принадлежит серверу; клиент получает его через `toDisplayRoomView` /
`toControllerRoomView` и раздаёт хуками. Локальное состояние интерфейса живёт в хуках рядом с тем,
кто им пользуется.

UI не читает объекты `@colyseus/schema` напрямую — только плоский разобранный view.

Одно исключение, и оно названо: `apps/display/src/game/` держит ссылки на объекты схемы. Иначе
нельзя — предсказание SDK выражается только на живых ссылках (`predict.value(entity, "x")`), а без
него корабль и мир оказываются на разных часах: корпус в настоящем, всё остальное на буфер позади, и
снаряд вылетает оттуда, где корпус был. Граница проходит по пакету: React-часть дисплея по-прежнему
видит только разобранный view, а сцена получает ссылки через один описанный каст в
`model/hooks/useShipPrediction.ts`.

## Что рисует картинку, а что рисует цифры

Правило одно и оно измерено, а не выведено: **`Graphics` — это инструмент рисования, а не объект
сцены.** Phaser обходит, триангулирует и батчит каждый `Graphics` **на каждом кадре, где он виден**,
сколько бы времени назад его ни нарисовали, и фигура (`add.circle`, `add.rectangle`, …) — тот же
`Graphics` под другим именем. Профиль живой волны на замедленной вчетверо машине показал графический
конвейер Phaser на двух третях главного потока и ни одной нашей функции в первых двадцати восьми
строках.

- Фигура с постоянной формой **запекается один раз** (`bakeShape` / `bakeRect` → `generateTexture`)
  и живёт на поле как `Image`: корпуса, стволы, снаряды, камни, препятствия, добыча, полосы HP,
  кольца фокуса, конус прицела, пол арены, щит. Меняться ей позволено только положением, углом,
  размером, тоном и прозрачностью.
- **Ширины линий внутри растянутой текстуры делятся на растяжение.** Пол арены печётся в 2048 и
  тянется до 4400 единиц, конус прицела — в 512 и тянется до дальности ствола; линия, нарисованная в
  мировой ширине, приезжает во столько же раз толще. Так конус один раз превратился в луч через весь
  экран.
- **`Graphics` остаётся** только там, где геометрия честно другая на каждом кадре и не выражается
  трансформацией запечённой: сейчас это лучи лазеров, чьи концы приходят с сервера каждый тик.
- **SVG не запрещён, но не для того, что движется с миром.** Радар был SVG на три сотни узлов,
  перестраивавшихся Реактом три раза в секунду, и стоил дороже всего остального интерфейса; в
  канвасе он стоит десятую часть. Текстовые панели в React — нормально: эталонный стенд держит сто
  миллисекунд React в секунду на двухстах коммитах и не роняет кадров. Дорого не количество React, а
  его комковатость.
- **Панель сравнивается по тому, что рисует, а не по тому, что приехало.** Нагрев ствола меняется
  шестьдесят раз в секунду, а полоска нагрева — это процент; сравнение сырого числа будило шапку и
  кокпит на каждом патче и делало их двумя самыми дорогими вещами на экране. Шаг сравнения крупный,
  плавность возвращает CSS-переход.
- **Быстрое значение живёт в своей подписке.** Если внутри панели есть одна величина, которая
  меняется на порядок чаще остальных, она выносится в отдельный лист со своим сравнением — иначе она
  тащит за собой всё, что рядом.

Прежде чем оптимизировать — **снять профиль**: `scripts/profile-display.mjs` говорит, куда уходит
кадр, `scripts/bench-panels.mjs` — что изменилось. Оба нужны с `--cpu=4` (этот десктоп без
замедления показывает 165 к/с и ноль рывков у любой версии) и оба **летят и стреляют**
(`scripts/fly-the-ship.mjs`), потому что неподвижный корабль меряет неподвижную картинку. На этой
ветке дважды очевидный подозреваемый — сначала React, потом аллокации — оказывался не тем, и профиль
решал вопрос за двенадцать секунд.

## Расширение вместо правки

Добавление нового варианта не должно требовать правки уже работающего кода. Практически это означает
таблицу вместо `switch` и данные вместо веток.

Эталоны в репозитории:

- `VISUAL_ASSETS_BY_ID` + `getVisualAsset` с фолбэком — новый силуэт добавляется записью данных,
  рендерер один на всех (`packages/protocol/src/visualCatalog.ts`);
- `override messages = { … }` — новое сообщение комнаты добавляется записью, диспетчера нет
  (`apps/server/src/rooms/SpaceshipDefenderRoom.ts`);
- `ROOM_DEFINITIONS` (`apps/server/src/roomRegistry.ts`);
- каталог архетипов врага: `EnemyKind` — это id, а не union, поэтому новый враг добавляется данными
  или прямо из консоли баланса;
- `SCREENS: Record<Tab, …>` в консоли баланса (`apps/admin/src/screens/registry.tsx`) — новый раздел
  добавляется записью, оболочка не правится.

При этом реестр вводится на **втором** независимом варианте поведения, не раньше. Три похожие строки
лучше преждевременной абстракции, а «расширяемость на будущее» без второго случая — это лишний слой,
который придётся сопровождать.

Если один и тот же факт приходится держать в двух местах (значение и подпись к нему, id и его
эффект), они должны стать одной записью.

**Маршрут объявляется записью в таблице, а не веткой.** Там, где таблица экранов уже есть, маршруты
выводятся из неё; писать вторым списком нельзя — он разойдётся с первым на первом же новом разделе.

## Адрес: путь называет экран, запрос настраивает его

Путь — это имя экрана. Прямой заход открывает экран, «назад» работает, ссылкой можно поделиться.
Стадия боя в путь не попадает: фазой владеет сервер, и адрес не имеет права стать вторым источником
правды о том, что происходит в игре.

Строка запроса — это настройка, а не адрес: `?diag`, `?tanks`, `?dpr`, `?demo`, `?wave`, `?ship`
остаются параметрами и в маршруты не превращаются. У их чтения **один источник — строка запроса
страницы**, потому что часть из них читается вне React (`SpaceshipCanvas`, сцена Phaser). Половина
из состояния роутера и половина из адресной строки — верный способ дать им разойтись.

**Переход обязан нести строку запроса.** Плотность пикселей и вариант арт-набора читаются в момент
постройки сцены, то есть уже после перехода: переход, потерявший запрос, ломает стенды замера и
демонстрационный прогон, не роняя ни одного unit-теста. Это самая дорогая ошибка в этой области,
потому что она молчаливая.

**Сессия комнаты живёт выше маршрутов.** Размонтирование её владельца закрывает сокет, поэтому хук
сессии вызывается над таблицей маршрутов, а не внутри экрана; переход после создания комнаты
заменяет запись истории, иначе «назад» вернёт на экран создания при живом соединении и следующее
создание откроет вторую комнату поверх первой.

## Границы, которые не двигаются

- `packages/game-core` — без DOM, Phaser, React, сети, часов и несеяного random. Время идёт через
  `advanceClock`, случайность через `createSeededRandom`.
- Phaser — только в `apps/display/src/game/`. Единственная точка входа — `SpaceshipRuntime`, наружу
  она отдаёт `update` / `prepareHydration` / `destroy` и принимает plain data.
- `packages/protocol` — единственный источник правды по контракту. Поле, которое едет по проводу,
  описывается там, а не дублируется на клиенте.
- Сервер авторитетен. Клиент шлёт намерения: непрерывный ввод несёт монотонный `sequence`, команды с
  тратой ресурсов — `actionId` + `revision`.

## Импорты

Внутри приложения — относительные пути с явным расширением `.js` (`./VirtualStick.js`), между
пакетами — по имени workspace (`@spaceship-defender/protocol`). Path-алиасов нет и не заводим.

Barrel-файлы внутри приложений не создаём: `packages/*` экспортируют свой `src/index.ts`, а внутри
приложения перечень реэкспортов только маскирует, кто чем пользуется.

## Тесты

Тест лежит рядом с исходником: `Foo.tsx` и `Foo.test.tsx` в одной папке. Переезжает файл —
переезжает тест.

Компоненты проверяются разметкой через `renderToStaticMarkup`; jsdom и Testing Library не добавляем.
Взаимодействие проверяется в `tests/e2e`. Чистые функции из `model/` покрываются обычными
unit-тестами — это основная причина, по которой вычисления не живут внутри компонентов.

`data-testid` и `data-*` на элементах display — контракт Playwright. Переименование только вместе с
правкой `tests/e2e` в том же коммите.

## Стили

Обычный CSS, один `styles.css` на приложение. Без CSS-in-JS, без UI-фреймворков. Классы глобальные,
поэтому при переносе JSX разметка и стили не расходятся — менять классы «заодно» не нужно.

## Язык и именование

Идентификаторы и комментарии английские. Строки интерфейса, продуктовые документы и артефакты
OpenSpec — русские. Ссылки на React-рефы называются `xxxReference`.

## Проверка

Полный гейт — `pnpm check` (format, lint, typecheck, test, build, smoke:network, e2e), для изменений
поведения дополнительно `pnpm spec:validate`.

На ревью проверяется глазами то, что не ловит линтер: файл лежит на своём уровне лестницы, `App.tsx`
не набрал логики, новый вариант поведения добавлен записью в таблицу, а не веткой, и ни один
`data-testid` не изменился молча.
